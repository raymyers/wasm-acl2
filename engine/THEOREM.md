# The engine's theorem: a guide for inspecting it

This is for a reader who wants to check, without taking our word, what
has been proved about the WebAssembly engine in this directory: what the
statement is, what each symbol in it means, how to have ACL2 confirm it,
and what it does not say. Every command here was run on 2026-11-18;
`inspect.lsp` is the script for sections 3 and 4.

## 1. The statement

Two theorems, both in [`run.lisp`](run.lisp), both about `engine-run`,
the function a driver calls to run a configuration of the specification
on the fast machine.

```lisp
; The engine follows the specification or stops.
(defthm engine-run-is-spec-steps
  (implies (and (config-shape-p c)
                (fmp fm))
           (equal (stepn (engine-steps n c fm) c)
                  (list (engine-config (engine-run n c fm))))))

; A result of the engine is the result of the specification (T3).
(defthm engine-run-is-spec-run
  (implies (and (config-shape-p c)
                (fmp fm)
                (engine-result-p (engine-run n c fm))
                (natp fuel)
                (< (engine-clocks n c) fuel))
           (equal (w3t::steps/%fuel fuel c)
                  (list (engine-config (engine-run n c fm))))))
```

In words:

- **Follows or stops.** Give the engine a configuration `c` and let it
  run for at most `n` of its own steps. However the run ends (a result,
  out of steps, stuck, an instruction it refuses), the configuration it
  is in is one that the specification's step function reaches from `c`
  after some number of steps. The engine is never somewhere the
  specification does not go.
- **Result.** If the run ends with a result (values, a trap, or an
  uncaught exception), that configuration is what the specification's own
  run function returns from `c`, given enough fuel.

The specification is the generated WebAssembly 3.0 semantics, package
`W3T`: `W3T::STEP` and `W3T::STEPS/%FUEL`, translated from the SpecTec
source of the standard (`../translate`). The engine does not have its
own semantics of an instruction; the theorem relates it to those two
functions.

## 2. Reading the statement

What each symbol is, where it is defined, and whether you need to read
its definition to know what the theorem says.

| Symbol | Defined in | What it is | Read it? |
|---|---|---|---|
| `c` | | a configuration `((store; frame); instr*)`, as the spec's `$instantiate` and `$invoke` build it | |
| `w3t::step` | `../translate/gen/wasm-3.0/4_3-execution_instructions.lisp` (generated) | one step of the specification: `(list c')`, or `nil` when `c` does not step | yes: it is what "the specification" means here |
| `stepn` | [`theorem/simulation.lisp`](theorem/simulation.lisp), 6 lines | `(stepn k c)`: `(list c')` if `STEP` succeeds exactly `k` times from `c`, else `nil` | yes |
| `w3t::steps/%fuel` | same generated file, 9 lines | step until `STEP` fails, at most `fuel` times; `(list c')` for the configuration that does not step, `nil` if the fuel runs out | yes |
| `config-shape-p` | [`fast/inv.lisp`](fast/inv.lisp) | the hypothesis on the input: the shape above, a store with all ten fields, a memory 0 that is a record with a byte list. Executable | yes: a hypothesis that is never true would make the theorem empty |
| `fmp` | generated by `defstobj fm` in [`fast/fast.lisp`](fast/fast.lisp) | "`fm` is a machine state object". ACL2 guarantees it of the live object; a theorem has to ask it of a variable | no |
| `engine-run` | [`run.lisp`](run.lisp), 3 lines | load `c` into the state object, run the fast machine for at most `n` steps | see below |
| `engine-config` | [`run.lisp`](run.lisp) | the configuration a state object stands for (`machine-abs` of `fm->ms`: the memory array put back into the store, the control stack unfolded into nested instructions) | see below |
| `engine-result-p` | [`run.lisp`](run.lisp) | the status is `:done`, `:trap` or `:throw` | yes, for the second theorem |
| `engine-steps` | [`run.lisp`](run.lisp) | a natural number: how many spec steps the run stands for. Not executable | no: read the theorem as "for some number of steps" |
| `engine-clocks` | [`run.lisp`](run.lisp) | a natural number that bounds the fuel. Read the hypothesis as "with enough fuel" | no |

Two remarks that save reading.

**You do not have to understand `engine-run` or `engine-config` to trust
a run.** The theorems are about whatever these two functions return. A
driver that calls `engine-run`, then reads its answer out of
`engine-config`, and nothing else, has an answer that is, by the
theorem, a configuration of the specification. So the thing to check is
not how the fast machine works (the stobj, the byte array, the fast
paths, 549 lines of `fast/fast.lisp`): it is that the driver calls
these functions and reads nothing else. Section 5 does that for the
slides.

**`engine-steps` cannot weaken the first theorem, and cannot strengthen
it either.** Whatever number it is, the equation says the engine's
configuration is `stepn` of that number from `c`. But the number may be
0: see the first point of section 6.

## 3. Have ACL2 confirm it

Inside `nix develop`, from the repository root:

```sh
make -C engine check
```

This certifies every book of the engine, each in a fresh ACL2, and
fails if one does not certify or if a book's source contains
`skip-proofs` or `defaxiom`. Expected last line:
`engine: no skip-proofs, no defaxiom in 36 book(s)`. The books are
`theorem/`, `lib/`, `machine/`, `rules/`, `fast/` and `run.lisp`; the
generated specification under `../translate/gen/wasm-3.0` is certified
first if it is not yet.

Then, from `engine/`:

```sh
sh bench/build.sh        # assembles the small test programs (wabt)
acl2 < inspect.lsp
```

`inspect.lsp` loads the certified `run` book and:

1. prints the two theorems and the definitions of section 2 **from
   ACL2's logical world** (`:pe`), so what you read is what was proved,
   not a copy in a document. Compare with section 1;
2. lists the books the theorems rest on whose certificate records a
   skipped proof, an axiom or a trust tag. Expected:

   ```
   INSPECT books 67 flagged NIL
   INSPECT skip-proofs-seen NIL
   <no ttags seen>
   ```

   The 67 books are the engine's, the generated specification's and the
   two system portcullis books they include. This check reads what ACL2
   recorded when it certified each book, so it also catches a
   `skip-proofs` hidden in a macro, which the `grep` of `make check`
   would miss;
3. evaluates both sides of both theorems on one program (next section).

## 4. See it on one run

`inspect.lsp` decodes `bench/wasm/fac-1.wasm` (the loop factorial of
[`bench/fac.wat`](bench/fac.wat)), instantiates it, and takes the
configuration `c` of the call `run(5)`. For several `n` it runs the
engine for `n` steps and compares, with `equal`:

```
INSPECT steps 0 hyps T status :RUN spec-steps 0 same T
INSPECT steps 3 hyps T status :RUN spec-steps 1 same T
INSPECT steps 21 hyps T status :RUN spec-steps 9 same T
INSPECT steps 89 hyps T status :RUN spec-steps 46 same T
INSPECT steps 144 hyps T status :DONE spec-steps 60 same T
INSPECT steps 1000 hyps T status :DONE spec-steps 60 same T
INSPECT result T fuel 61 same T instrs ((:CONST (:I64) 120))
```

- `hyps`: `(config-shape-p c)` and `(fmp fm)`, the hypotheses, evaluated.
- `same` on a `steps` line: `(stepn spec-steps c)` is
  `(list (engine-config (engine-run n c fm)))`: the first theorem's two
  sides. The engine stopped after `n` of its steps, in the middle of the
  program, and the specification stepped `spec-steps` times from `c` is
  in the same configuration, memory included.
- `same` on the `result` line: `(w3t::steps/%fuel 61 c)` is
  `(list (engine-config ...))`: the second theorem's two sides. The
  instructions left are the value 120.
- 89 engine steps are 46 spec steps: pushing a value and entering a
  block are steps of the engine and not of the specification.

This is a test, on one program, of statements that are proved for all.
It is here to show what the statements mean on real data, and it would
catch a theorem that says less than this guide claims. `spec-steps` is
`engine-clocks`, which is `engine-steps` for a run that is not refused;
`engine-steps` itself cannot be evaluated.

## 5. Is the engine that runs the one in the theorem?

For the slide renderer (`slides/`), yes, and it can be checked by
reading one file. [`slides/render.lsp`](slides/render.lsp) calls, of the
fast machine, only `config-shape-p`, `fmp`, `engine-run`,
`engine-result-p` and `engine-config` (from the repository root):

```sh
grep -o "(engine-[a-z-]*\|(fast-[a-z-]*\|(fm[a-z>-]*\|(config-shape-p" engine/slides/render.lsp | sort | uniq -c
```

(`(fm` alone is the state object in an argument list. The same file can
run the older list machine instead, with `ENGINE=list`; those calls are
`machine-*`.) Every pixel is read from the configuration `engine-config`
returned.

```sh
make -C engine slides
```

prints, for each of the 12 runs (instantiation, four small calls, seven
slides), `ENGINE-T3 config-shape T fmp T result T`: the hypotheses of the
second theorem, evaluated on that run. So for each run the theorem
applies, and the pixels are the specification's. The script also
compares each slide with V8's rendering of the same module: 7 of 7
identical.

For TeX (`tex/`), no: see section 6.

## 6. What the theorems do not say

Ways in which a reader could take them for more than they are.

- **They do not say the engine makes progress.** An engine that stopped
  at once would satisfy "follows or stops" (`engine-steps` would be 0).
  That the engine gets to the end is observed, not proved: the run of
  section 4 ends `:DONE`, the slides render. What is proved is that
  where it reports a result, the result is right, and that it is never
  wrong on the way.
- **One direction.** When the engine stops without a result (`:stuck`,
  `:unsupported`), nothing says that the specification stops there too.
  It may step on.
- **"The specification" is the generated semantics.** That `W3T::STEP`
  is the WebAssembly standard rests on the translator and on SpecTec
  (`../plan/wasm3-translation/evidence.md`), not on these theorems.
- **Host functions.** At a call of a host function the engine stops
  `:unsupported`. A program with host calls gets "follows or stops" up to
  its first host call and no result. `tex.wasm` is such a program: the
  TeX driver resumes the engine after each host call with Lisp code of
  its own, which no theorem covers ([`tex/README.md`](tex/README.md)).
- **A module with no memory** does not meet `config-shape-p`.
- **Instructions.** No instruction is excluded by a hypothesis. An
  instruction the engine has no rule for makes it stop `:unsupported`,
  which is the "stops" of the first theorem.
- **Before and after the run.** Decoding the module and building the
  configuration are the specification's own functions (`GRAM/BMODULE`,
  `$instantiate`, `$invoke`), run as they are. The first two are in
  program mode, so no theorem starts from the bytes of a module; the
  theorems start from the configuration.
- **Trusted throughout**: ACL2 and SBCL, including ACL2's execution of a
  state object in place.

## 7. Where the proof is, for a reader who wants to follow it

The statement needs none of this. Each row is proved from the rows
above it; the names are theorems you can print with `:pe`.

| Layer | Book | Theorem |
|---|---|---|
| Any machine with four properties computes the spec's results | `theorem/simulation.lisp` | `engine-result-is-spec-result`, `m-run-simulates` |
| The list machine (lists, the spec's own rule functions) has them | `machine/spec-result.lisp` | `machine-step-simulates`, `machine-result-is-spec-result` (T1) |
| One step of the fast machine is one step of the list machine, or is refused | `fast/call-ref.lisp` | `fast-step-is-machine-step` |
| A refused step changes only the status | `fast/stretch.lisp` | `fast-step-when-refused` |
| The fast machine's invariant is kept by a step and holds after loading | `fast/inv.lisp` | `fast-step-keeps-fm-inv`, `fm-inv-of-fm-load-ms` |
| A run of the fast machine, result or not | `fast/spec-result.lisp`, `fast/stretch.lisp` | `fast-result-is-spec-result` (T2), `fast-run-is-spec-steps-or-refused` |
| The engine as it is called | `run.lisp` | the two theorems of section 1 |

The history, with what failed on the way and every measured number, is
in `../plan/wasm-engine/plan2.md` and its notes.
